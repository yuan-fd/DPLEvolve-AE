# Teacher Follow-Up Rules

Use prior Teacher session context as memory. Read only current iteration
context, peer packet, review packet fields, and targeted source/metric excerpts
needed for routing. Do not restate global policy unless it changes the next
decision.

## Objective

- Legal final `metrics.json:hpwl` is the elite/promotion target. `G_HR` is
  analysis-only for runtime value.
- Keep 5% final-HPWL reduction versus OpenROAD default as search ambition. If
  the current best is far below that, route mechanism-level quality expansion,
  not donor preservation, guard work, or small polish.
- Runtime is a hard budget and secondary value check. Runtime repair is useful
  only when it frees budget for a stronger named HPWL mechanism.
- Treat `HPWLlg` as diagnosis. Legalizer follow-up must preserve final HPWL,
  legality, displacement tails, DPO recoverability, and exact accepted gain.

## Routing Basis

- Route from stage-wise evidence, logs/counters, source behavior, Student
  knowledge-card reasoning, and peer evidence. Current evidence wins over old
  knowledge.
- Before assigning Students, name the dominant HPWL source in one phrase:
  legalizer producer quality, DPO consumer strength, handoff/frontier loss,
  post-consumer preservation, or composition.
- Weak-result diagnosis is mandatory. Classify the blocking bucket:
  non-executed/stale code, producer payload quality, handoff lifetime, DPO
  consumer zero/low accepts, strict/local acceptance, accepted-delta washout,
  post-consumer preservation loss, runtime/cap bottleneck, wrong start/case
  route, or validated-low-ROI.
- Nonzero counters and accepted delta prove liveness, not quality sufficiency.
  If final HPWL remains weak or far from ambition, route a stronger chain link
  or a different HPWL source.
- If a Student card lacks source inspection plus metrics/log diagnosis, treat it
  as under-diagnosed and require code/log diagnosis or a concrete missing-chain
  repair before promotion.

## Route Shape

- Assign one primary mechanism hypothesis per Student with 1-3 first-patch
  handles for orientation. Handles are not an allowed-file list; Students may
  modify any private `dpl_evolve` file needed by one coherent producer,
  handoff, consumer, objective, transaction, mirror, helper, parameter, or
  telemetry mechanism.
- First-patch handles should include the source-understanding target: entry
  point, state/payload lifetime, consumer/acceptance path, and proof counter/log
  when the route depends on a nontrivial path.
- Label every packet with `route type` and `route action`: `repair`,
  `switch`, `hybridize`, `mechanism-redesign`, or `elite-expand`.
- Route the current best as `elite-expand` only when it names a stronger
  donor-on-top quality mechanism. Preservation is rollback discipline, not the
  assignment.
- Same-family continuation is valid only when it changes mechanism class or
  repairs a proven implementation/handoff bug, not just thresholds, tie-breaks,
  counters, or local polish.
- If a legal donor remains weak after one meaningful continuation, assign at
  least one Student to a complete strong-chain reconstruction or alternate
  start basin. Diagnose with final HPWL plus accepted-delta/runtime evidence,
  not only accept count or `HPWLlg`.
- If a rejected mechanism is implementation-bug or handoff-repairable rather
  than method-low-ROI, assign a repair trial from its ref with
  `25_trial_source.sh begin --from-ref <ref>`.

## Pipeline Coverage

- Each optimization packet should include `pipeline coverage`: producer /
  legalizer action, handoff / frontier action, and consumer / DPO action. At
  least two entries should be active source mechanisms or liveness hooks.
- A `co-optimization-emphasis` packet should make all three links active unless
  current evidence justifies leaving one stage untouched.
- Route emphasis is not stage exclusion. A Student can prioritize one surface,
  but the packet should say how adjacent stages consume, preserve, or validate
  that mechanism.
- Do not route a whole roster to one DPO family, one legalizer family,
  mirror-only preservation, runtime-only cleanup, or same-basin variants when
  compatible live mechanisms can be combined.
- Mirror work is support only. Pair it with accepted DPO/reorder/handoff gains
  that need protection or attribution; otherwise keep mirroring callable and
  spend the route on legalizer/DPO/handoff sources.

## Knowledge And Blueprints

- Do not send Students into broad knowledge-base reading by default. If
  knowledge is needed, name the specific card/blueprint/query and the exact
  mechanism question it answers.
- Use blueprints as route hypotheses or compatible mechanism components, not as
  fixed selectors. A case may match multiple feature-level blueprints.
- When a route keeps or switches to Blueprint A/B/C/D or D+A, include a
  complete-chain audit: selected blueprint/start basin, producer payload,
  handoff state, exact consumer, post-consumer closure, required counters,
  already-live links, missing links, and this Student's repair target.
- Name the exact stack query for blueprint or stacking routes, normally
  `08_query_knowledge.sh --stage teacher_review --q "Blueprint <letter|D+A> stack"`.
  Use the returned `compatible_with` and `failure_buckets` fields to justify
  whether the next packet continues, stacks, repairs, or switches.
- For Differential/LEGALM-style guidance, the target objective is searchable.
  If logs show zero useful moves, missing frontier consumption, or final-HPWL
  damage after DPO, route a target/weight/stop/handoff/consumer change rather
  than repeating the same objective or discarding the family.

## Follow-Up Discipline

- Use the first-round route map as memory, but do not forget untested routes.
  If the best family stalls, name the observed failure mode and assign a
  new-family route from evidence.
- Prefer same-case mechanism stacking when evidence shows real final-HPWL
  movement: combine a live producer with a consumer, add compact handoff to a
  proven exact move family, or rewrite a strong heavy donor for bounded runtime.
  If a stack card exists, route only compatible links from that record unless
  current source evidence gives a stronger local compatibility proof.
- Each non-repair route must explain why it can beat a small donor by attacking
  a larger HPWL source.
- Each route needs an expected stage-wise proof target: `HPWLlg`,
  `HPWLimprove`, `HPWLfinal`, and counters that should prove execution. For
  legalizer routes, include avg/max displacement and downstream DPO accepted
  gain expectations.
- Encourage coherent mechanism-level source rewrites when justified; the
  constraint is bounded, reviewable, and measured, not small.
- Require efficient implementation paths: capped candidates, cached/touched-net
  scoring, compact frontier state, affected-net deltas, deterministic probes,
  or other cost controls. Do not assign "try more DPO work" without a new HPWL
  source hypothesis.
- Avoid repeated micro-optimization loops. If a live, correct mechanism still
  has tiny full-flow HPWL movement after one meaningful repair, mark it
  `validated-low-ROI` and route a different HPWL source.
- Prepared starts are branch-only source parents: `framework`, `diamond`, and
  `default_negotiation`. A start branch never restricts edit scope, and
  Students should not manually apply release/start patch files.
- Keep packets non-accumulative: one HPWL source, concise dominant mechanism,
  pipeline coverage, first-patch handles, minimal support handles, runtime
  tier, liveness counters, low-ROI stop rule, and metric proof. Replace stale
  guidance instead of appending history.
